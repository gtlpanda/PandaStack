# SA-02c journal-owned grant and pause controls — proposal, not frozen

External preparation only. Depends on corrected/accepted SA-02a and SA-02b. No implementation or execution. Keep the existing journal owner, lease, database transactions, immutable invocationLimit, receipt states, identity checks and legacy API behavior.

## Small feature split

C1: additive journal-owned control record, CAS grant/pause methods, actual partial-report freshness acknowledgement and unchanged receipt replay/settlement. Tests below exercise only ordinary disposable fixtures and fake in-process leaf callbacks.
C2: native host integration with existing scheduler budget/reserve policy, publication after every terminal callback, continual call/usage presentation and actual pause/resume. C1 alone does not claim verification reserve enforcement or native callback integration. No new owner class/sidecar scheduler.

## Explicit opt-in and exact proposed methods

Existing openAuditJournal({runDir,invocationLimit}) unchanged. For NEW native runs invocationLimit is the configured maximum total calls; this is not initial spend authorization. Existing journals continue enforcing their original immutable limit until explicit initControl. No reopen option changes the maximum.

Add to existing owner:
- initControl({initialGrant}) -> control. Explicit one-time transaction, only with zero attempt rows and no existing control; grant integer0..invocationLimit. Repeated initialization CONFLICT, no implicit migration. Initializes revision1 and blocker report_stale. Existing populated journals cannot opt in through this slice (CONTROL_INIT_REFUSED); continuation/migration separate.
- getControl() -> null for legacy or detached control.
- adjustGrant({expectedRevision,currentGrant,reason}) -> control. CAS, safe integer0..maximum, not below settled+held; reason exactly operator_increase; new grant must be strictly greater than stored grant (decrease/equality INVALID_CONTROL_INPUT). Requires paused_budget already set AND no dispatched/uncertain rows: otherwise CONTROL_BUSY. Merely having no active row does not authorize an adjustment. Never edits invocationLimit, receipts, IDs, spend or identity. Adds report_stale; does NOT clear other blockers.
- pauseControl({expectedRevision,reason}) -> control, reason report_stale/paused_budget/paused_uncertain. Adds blocker; CAS still checked on idempotent addition, no-op returns same revision.
- acknowledgeReport({expectedRevision}) -> control. No caller generation, boolean, callback or reader injection. Calls actual owning readPartialReport(runDir); requires status current with a valid generation key and current evidence digest, otherwise REPORT_NOT_CURRENT with no mutation. Only removes report_stale, leaves other blockers intact. Current-source recheck at serialized owning host boundary before control CAS; never hold DB transaction across renderer/reader recursion.
- resumeBudget({expectedRevision}) -> control. Requires no dispatched/uncertain rows and grant >settled+held; otherwise CONTROL_BUSY/BUDGET_EXHAUSTED. Removes only paused_budget; report_stale and paused_uncertain remain. C2 rechecks actual stage reserve before dispatch; this method alone never certifies reserve sufficiency.

Read-only export readAuditControl(runDir) -> null|control uses same corrected full identity comparison as readAuditJournal; never creates DB or owner. All methods require existing live owner and current bound identity. Legacy readAuditJournal result shape stays unchanged.

Control exact {version:1,revision,maximum,currentGrant,blockers,acknowledgedGeneration}. maximum equals immutable invocationLimit. blockers sorted lexical unique subset of three reasons; acknowledgedGeneration null or64hex. Any real control mutation increments safeinteger revision by1. Invalid inputs INVALID_CONTROL_INPUT; stale revision CONFLICT. Corrupt/unrecognized stored control schema CORRUPT, no fallback to legacy. Durable schema upgrade and control table creation atomic under existing owner; old journals without control record remain legacy, not corrupt. History rows preserve revision, old/new grant, reason and before/after blockers, bounded by existing1GiB logical budget; no wallclock required.

## Same admission gate; no lost results

For controlled journals, new prepare and prepared->dispatched execute transaction both reject CONTROL_PAUSED if any blocker. New prepare additionally requires settled+held <currentGrant and immutable maximum. A grant exhaustion refusal atomically adds paused_budget before returning BUDGET_EXHAUSTED; no attempt row/callback. Existing identical prepare can return existing row while paused (no new reservation). Existing changed-input prepare still CONFLICT. Prepared execution is already charged; it does not require an additional free slot, only totalcharge<=grant and no blockers.

Terminal returned/failed replay remains allowed under every blocker with no callback; settlement of already dispatched callbacks always remains allowed. cancelPrepared can release only never-dispatched rows while paused; it never clears blockers automatically. Unknown/dispatched authority stays charged. On any controlled terminal settlement add report_stale in the SAME transaction as receipt. If outcome uncertain, additionally add paused_uncertain. On reopen converting dispatched to uncertain, add both blockers. No method in this feature clears paused_uncertain: separate actual reconciliation must determine outcome; neither extra grant nor a current report proves execution terminal. No raw verified flag/boolean exemption.

Multiple in-flight callbacks may settle while paused, each durably recorded; new calls cannot start. Host renders after each terminal callback and refreshes acknowledgement. A late terminal result is never converted into provider failure because report publication failed.

## Report evidence projection without circular acknowledgement

Add readAuditBudgetEvidence(runDir) -> null|{version:1,maximum,currentGrant} through journal owner. SA-02b context binding adds this canonical projection to its validated journal evidence; partial prose labels maximum versus authorized grant distinctly. Receipts/rows already bind settled+held. Bind projection null for legacy. Changing grant therefore invalidates old report. Exclude control revision/blockers/acknowledgedGeneration/history from report generation digest AND rendered report content. Those live control details are shown separately by getControl/CLI with their revision, not falsely bound to immutable report prose.

Acknowledgement writes only excluded control bookkeeping, so does not invalidate the generation it acknowledges. It must compare actual reader current at the owning serialized boundary, not trust a supplied digest. Failure to read journal/budget projection makes report invalid/unknown as SA-02b specifies. No raw SQL fallback. Source/artifact changes continue to invalidate report independently.

## Exact additive schema transition and reserved capacity

Storage retains application_id 0x53414a31. Legacy user_version1 remains the existing exact header/attempts schema, validated byte-for-byte as today. Controlled user_version2 retains those exact two CREATE statements and adds exactly:
CREATE TABLE control (singleton INTEGER PRIMARY KEY CHECK(singleton=1), body TEXT NOT NULL) STRICT
CREATE TABLE control_history (revision INTEGER PRIMARY KEY, body TEXT NOT NULL) STRICT
No extra views/triggers/indexes/table definitions or other user_version accepted. Existing SQLite internal sqlite_% handling unchanged. Control body is canonical JSON of the public control object plus private reservedHistorySlots safeinteger; history body is canonical JSON {reason,oldGrant,newGrant,beforeBlockers,afterBlockers,acknowledgedGeneration}, with row revision the corresponding public revision. Reason is an exact owning enum (init,operator_increase,report_stale,paused_budget,paused_uncertain,ack_report,resume_budget,settled,recovered_uncertain). Each body <=1024 UTF8 bytes; control <=4096 bytes. Validate lengths before materializing contents.

initControl performs schema verification, empty attempts assertion, both CREATE statements, initial control/history rows, and PRAGMA user_version=2 within one existing BEGIN IMMEDIATE transaction under the original lease. On failure rollback leaves version1 and both original schemas/bytes logically unchanged; report no success if commit/durability uncertain. Normal open/read may accept validated v1 or v2, but NEVER upgrades automatically. Calling initControl on version2 is CONFLICT. Owner reopen still requires original immutable invocationLimit. No new lock, lease or owner.

Control space reserve is fixed CONTROL_BYTES=4096+32768*1024 logical bytes within the same 1073741824 limit, charged from explicit init onward even if not physically allocated. Maximum32768 immutable history rows; no pruning/rewrite. Ordinary control mutation needs one unreserved history slot; insufficient space returns CONTROL_CAPACITY before any mutation or acknowledgement.

Each admitted prepared row reserves one history slot for its eventual settlement/recovery transition and a full BODY_LIMIT result allowance in addition to its current input/row logical charge. Admission fails INPUT_TOO_LARGE before row creation if the controlled1GiB accounting (including full control reserve and pending result allowances) cannot cover it. Pending/uncertain rows retain their result allowance. A terminal returned/failed row uses its actual bytes and releases unused result allowance; cancelPrepared releases its unused allowances. These are conservative NEW controlled-run admission rules; legacy accounting is unchanged.

Nonterminal control actions cannot consume reserved settlement history slots. One terminal/uncertain settlement combines receipt and blocker update into ONE reserved history event in the same transaction; report-stale plus uncertain is not two events. Reopen recovery uses the affected row's reserved slot; a row already uncertain does not consume another recovery event. Exact reservedHistorySlots equals prepared+dispatched rows requiring their first settlement transition, not already uncertain rows whose reserved event was consumed. Prepared cancellation releases its unconsumed slot. Result allowance for uncertain remains charged separately. No decrement or reuse of existing immutable history revisions.

Real filesystem/SQLite I/O failure can still prevent commit. Return IO_ERROR, no fake durable receipt, acknowledgement or control success; owning callback result remains persistence-uncertain and must not authorize retry. Capacity reservation is not a guarantee against disk failure. A preflight CONTROL_CAPACITY/INPUT_TOO_LARGE cannot prevent an already admitted callback from using its reserved slots/bytes. Independent source review must trace this, without huge database fixtures or race probes.


Reservation bookkeeping precision: successful prepare/cancelPrepared changes reservedHistorySlots and attempt rows atomically but does NOT increment public control revision or append control_history; it does not change public control fields. Binding/freshness still changes through journal rows. A rejected reservation that sets paused_budget IS a public control transition and consumes one unreserved history slot/increments revision. Terminal settlement/recovery updates blockers and consumes its reserved history slot/increments revision even if report_stale already exists, so each consumed settlement slot has one immutable history event. CAS methods validate current rows/accounting inside their transaction as well as public revision; an unchanged public revision never licenses ignoring changed holds. Control revision tracks control transitions, not every journal mutation.


C2/NR02 boundary prerequisite: frozen NR02 currently treats reserve exceptions as fatal CHECKPOINT_ERROR and aborts active leaves. A budget/report admission pause instead needs a separately reviewed pause-port extension or explicit owning adapter behavior that stops NEW permits and drains in-flight durable outcomes without false graph completion. Do not modify frozen NR02 in C1, convert pause into ordinary leaf failure, or claim current runtime already drains correctly. Full C2 acceptance must exercise the real runtime distinction before controlled native runs launch.
