Security remains first. All offerings include marketing. This plan does not claim parity or authorize execution/installation. It decomposes the user requirement against the exhaustive installer inventory. ## Common fixture matrix

### entry

- Clean Codex-only HOME/skill root resolves owning entry and local dependencies
- No accidental ~/.claude lookup or Claude fallback; explicit unsupported prerequisite fails before dispatch

### permissions

- Use supported native tools and scopes; role prompt cannot grant tool authorization
- No extra remote sends/merge/deploy/purchase; preserve existing approval boundaries

### modelConfig

- Selected orchestrator/advisor/worker/probe config reaches actual owning leaf; model/effort availability never inferred from a label
- Explicit unsupported controls rejected or honestly reported; no invented dollar budgets or nested-cap enforcement

### recovery

- Persisted graph state and valid completed siblings retained; in-flight uncertainty cannot cause blind replay
- Guidance-only flow preserves written artifacts and explains interrupted/partial work; no invented durable process promise

### outputs

- Structured outputs pass unchanged owning validators; error/partial stays distinguishable from success
- Readable reports reflect current evidence/generation and retain source-only/unknown limitations

## Installation and capability catalog contract proposal

One versioned program-owned catalog supplies installer selection, doctor output and entry routing. It is data about supported machinery, never user permission. Catalog input must not select arbitrary modules, executables or tool authorities. Root must approve exact API/schema before tests freeze.

Proposed catalog entry: `{id,kind,entry,providers,dependencies,stages,outputs,recovery,permissionProfile,proofRefs}`. `id` unique safe ID; `kind` one of graph/cli/guidance/reference/role/alias/presentation; `entry` owned repository-relative registered path; `providers` maps claude/codex to `{implementation: supported|partial|unavailable, transportId: registered ID|null, limitations: fixed codes}`. `dependencies` names catalog IDs and fixed tool capability IDs; no shell commands from catalog/user data. `stages`, `outputs`, `recovery` name the reviewed contract checkpoints. `permissionProfile` references a trusted program-owned profile, not inline grants. `proofRefs` reference reviewed test/evidence IDs and revision/hash; merely providing a ref does not validate it. Supported implementation status is release-maintained; current-host readiness is separately observed.

Proposed `inspectOffering({offeringId,provider,configuration}) -> {status:ready|unsupported|unknown,checks,limitations}`: host loads catalog itself and selects fixed inspectors. Missing tool/config is unsupported or missing prerequisite, inspection error unknown; never ready by absent observation. Check exact selected executable/path, module dependency resolution and supported model/effort evidence where dispatch requires it. Offline inspection never starts a provider; explicit owned capability probe is separately bounded/authorized and records what the API accepted, not internal model identity. Guidance/reference entries require readable entry/dependency files and supported tools actually needed for the representative task; no provider process required for static content.

Clean installer tests must cover all catalog entries by their intended kind, skip/backups/conflicts/uninstall, symlink/unsafe destination refusal, absence of HOME, paths with spaces/colon and local platform support. No blanket import of Claude hooks/settings. Preserve command aliases and source paths through registered resolution. Verify effective dependency closure, not just SKILL.md symlink. Newly offered entries not yet implemented must remain explicitly unavailable/partial; user requirement stays incomplete until required executable/guided offerings have their proper proof.

`init-claude` remains the named CLAUDE.md generator. Provide `init-codex` alias or neutral `init-agent --provider` that selects equivalent native AGENTS/config output with the same project facts. Do not overwrite existing Claude files as a side effect. Test both providers and already-existing mixed setup; configuration must use actual supported native mechanisms, not copied settings keys.

Standalone agents are role templates, not 37 autonomous products. Exercise actual native invocation/tool restrictions for each role family and retain all instructions; external-service roles need mock connector/CLI fixtures and explicit action authority. AWS architecture and founding-sales command aliases are included; marketing outreach templates never authorize sends. Statusline is a presentation integration: if native runtime has no equivalent, disclose gap and choose a supported native status surface before claiming full presentation parity.

## Explicit provider constraints and cost observability regression

Supported native constraints must be applied by their actual owning runtime, with evidence of effective selection.
